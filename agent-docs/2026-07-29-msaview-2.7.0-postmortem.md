# Post-mortem, 2026-07-29 — msaview 2.7.0 error-paged every released host

Not an ADR: this records what happened and how to reproduce it. The decisions it
drove are
[ADR 0002](architectural-decision-records/0002-two-url-shapes-two-rollback-levers.md)
(a rollback needs both levers) and
[ADR 0003](architectural-decision-records/0003-boot-bundles-rather-than-trust-declared-ranges.md)
(boot bundles instead of trusting declared ranges).

## What happened

msaview 2.7.0 was promoted here, which published it to `latest/`. Every
`jbrowse.org/ucsc` launch on v4.0.0 through latest became an error page —
`PluginLoader` runs `Promise.all` over the plugin list, so one bundle that
throws while loading takes the whole session down, not just its own features.

`latest/` was rolled back to 2.6.8 for a few hours (`ebc8eb7`). 2.7.1 fixed it
and no pin remains.

## Two causes, both from building against an unreleased `@jbrowse/core`

The plugin was built against a core carrying MUI v9, which no released host has.

- **`@mui/material/SvgIcon` was externalized, but its exported _shape_ differs
  by MUI major.** Released hosts expose it as the SvgIcon component (`$$typeof`,
  `render`, `displayName`). MUI 9 additionally hangs `createSvgIcon` off it,
  which `@mui/icons-material` v9 calls. A key-presence check sees nothing wrong
  — the key is there on every host. Fixed by bundling that module into the
  plugin.
- **`types.stripDefault` exists only in the mobx-state-tree that ships with
  unreleased core.** react-msaview 5.6.3 degrades to `types.optional` where it
  is absent.

Neither is expressible as a version range, and neither is caught by asking
whether a symbol exists. **Shape, not presence, is what varies.**

## Why the plugin's own CI passed

It tested `[v3.7.0, nightly]` — the two ends. The failure lived in the middle,
v4.0.0 through latest. `nightly` is also the same unreleased core the author
develops against, so it was the one host guaranteed not to reproduce the bug.

## What the rollback missed

`ebc8eb7` changed 12 files, all under `dist/jbrowse-plugin-msaview/latest/`. It
touched neither `plugins.json` nor the manifest, so the store went on offering
**2.7.0** — verified by reading `v2_plugins.json` at that commit; it only moved
to 2.7.1 at `f29ec33`. For the whole window, anyone clicking _Install MsaView_
received the bundle that error-pages.

Rolling back `latest/` covers configs. Pinning `versions` in `plugins.json`
covers store installs. They are separate levers over separate populations; see
ADR 0002.

## Reproducing it

`check-plugins.ts` reproduces the break exactly:

```
node fetch-version.ts jbrowse-plugin-msaview 2.7.0
node check-plugins.ts --only jbrowse-plugin-msaview \
  --bundle jbrowse-plugin-msaview=dist/jbrowse-plugin-msaview/2.7.0 \
  --versions v4.0.0,v4.3.0,latest
# v4.0.0  FATAL ... JBrowsePluginMsaView is undefined
```

`fetch-version.ts` is needed first because `dist/` no longer keeps superseded
versions (ADR 0005). `--bundle` also accepts a plugin repo's own `dist/`, so a
candidate build can be checked before it is published to npm at all.

For a break that only shows up with real config content — an unknown track type,
a plugin's menu contribution — jb2hubs' `checkConfigCompat.mjs` boots the actual
shipped configs and takes the same `--plugin Name=path` override. This repo's
checker deliberately uses an empty config so a failure names one bundle.

## The lesson, stated so it does not get misread

It is **not** "pin things." Pinning is the emergency lever, not the strategy.
The strategy is that a compatibility claim cannot be trusted, because the thing
that varies between hosts is the shape of what they export, and only booting the
bundle on a real host observes that.
